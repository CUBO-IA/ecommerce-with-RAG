# Architecture

This application is a Next.js App Router storefront with PostgreSQL product data, RustFS object storage for images, and AI-assisted product discovery.

## Major layers

### Routes and UI

- `/` is rendered by `app/page.tsx`. Its server-side `ProductGrid` calls `listProducts()` and renders each result with `src/components/ProductCard.tsx`. Each card links to `/product/{id}`.
- `/product/[id]` is rendered by `app/product/[id]/page.tsx`. It accepts numeric IDs, loads the product with `getProduct()`, returns `notFound()` for an invalid or missing product, and passes the product to `src/components/AddToCartButton.tsx`. Product image URLs are returned by the product layer and used directly by `next/image`.
- `/admin/products` is rendered by `app/admin/products/page.tsx`. The client component `app/admin/products/product-form.tsx` invokes the server action in `app/admin/products/actions.ts`; the page also lists products and submits deletions. The route currently has no authentication; the source comment identifies it as a proof of concept.
- `src/components/ProductCard.tsx` is a presentational component. It renders full and compact product cards from already formatted display data; it does not query storage or the database.

### Product and search layer

`src/products/index.ts` is the product boundary used by the routes and chat tools. It:

1. Validates the product name, description, and price with Zod; `createProduct()` separately checks the image MIME type and 5 MB size limit. Prices submitted in dollars are converted to integer cents.
2. Uploads the image through `src/s3/client.ts`.
3. Requests a floating-point embedding for the 2048-dimensional database field using the product name and description through `src/ai/openrouter.ts`.
4. Stores the product row and embedding through `db.orm.public.Product`.
5. Maps the stored `imageKey` to a public `imageUrl` before returning product data; the internal key is not exposed by the returned object.

If embedding or database creation fails after the image upload, `createProduct()` deletes the uploaded object before rethrowing. Explicit product deletion removes the database row and then its image object. Product list, detail, and search reads return `id`, `name`, `description`, and `priceCents` plus the derived public image URL.

The two search paths are:

- `src/products/lexical.ts` searches the Spanish full-text representation of `name` and `description` using PostgreSQL `websearch_to_tsquery`, applies inclusive price bounds, and orders by `ts_rank`.
- `src/products/nearest.ts` applies the price bounds and uses the ORM's `embedding_nearest` operation to rank products by vector similarity. `src/products/index.ts` documents a sequential scan: the `vector(2048)` field exceeds the pgvector dimension limit for HNSW/IVFFlat indexes, so the current implementation does not use one.

### Database and object storage

`src/prisma/contract.prisma` defines the `Product` table contract: an autogenerated integer ID, name, description, integer `priceCents`, an object-storage `imageKey`, optional `Embedding2048`, and `createdAt`. `prisma.config.ts` binds this contract to `DATABASE_URL`, configures the pgvector extension, and places migrations in `migrations`.

`docker-compose.yml` supplies the local persistence services:

- `db` runs `pgvector/pgvector:pg17` on port 5432 and persists data in the `pgdata` volume.
- `rustfs` provides S3-compatible storage on port 9000, with its console on port 9001, and persists objects in `rustfsdata`.
- `rustfs-init` creates the `products` bucket and grants public `s3:GetObject` access to objects in that bucket.

`src/s3/client.ts` connects to the configured S3 endpoint with path-style addressing, using `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, and `S3_BUCKET`. It stores JPEG, PNG, and WebP uploads under random UUID keys and builds public URLs from `S3_PUBLIC_URL`.

### AI integrations

- `src/ai/openrouter.ts` uses `OPENROUTER_API_KEY` with model `nvidia/nemotron-3.5-embed-1b:free` to return floating-point embeddings. These embeddings are used when creating products and for semantic search.
- `src/ai/anthropic.ts` configures `ANTHROPIC_API_KEY` with model `claude-haiku-5-5` as the chat model.
- `src/ai/chat.ts` defines the chat instructions and tools. Its system prompt limits responses to short Spanish plain text about the store. The tools can perform lexical or semantic product searches, open or retrieve a product, return a product for adding to the cart, summarize the cart, and retrieve a built-in sales guide. Search price arguments arrive in dollars and are converted to cents before reaching the product layer.

## Request and data flow

### Catalog and product detail

1. A request reaches the Next.js page for `/` or `/product/[id]`.
2. The page calls `listProducts()` or `getProduct()`.
3. The product layer reads PostgreSQL through the ORM and maps each `imageKey` to a RustFS public URL.
4. The page renders the product card or detail view. The browser loads the image from that public object URL.
5. Adding an item is handled by the client cart state described below.

### Product administration

1. The browser invokes `createProductAction()` through the `/admin/products` form.
2. The server action validates the image presence and calls `createProduct()`.
3. The product layer uploads the image to RustFS, requests an OpenRouter embedding, and writes the product and embedding to PostgreSQL.
4. The action revalidates `/` and `/admin/products`. Deletion performs the inverse database/object-storage cleanup and revalidates the same paths.

### Chat

1. A client sends `POST /api/chat` with a non-empty `messages` array and optional `path` and `cart` values.
2. `app/api/chat/route.ts` validates the request and UI message history; invalid JSON, body, cart, or history returns HTTP 400. It then loads the currently viewed product when `path` matches `/product/{id}` and adds catalog context when `path` is `/`.
3. The route invokes Anthropic with the tools from `src/ai/chat.ts`, permits up to four model steps, has a 60-second duration limit, and returns a streamed UI response. Streaming errors are logged server-side and converted to a short fallback response.
4. Product-search, product-detail, and cart tools query PostgreSQL through the product layer. Semantic search first requests an embedding from OpenRouter; lexical search queries PostgreSQL full text. `viewCart` receives the browser-supplied cart IDs and quantities, re-reads current product names and prices from PostgreSQL, and calculates the total.

The chat `openProduct` and `addToCart` tools only look up products and return data. The browser-side UI in `src/components/ChatWidget.tsx` turns those outputs into navigation or a cart mutation; the server does not mutate the cart.

## State ownership

- **Persistent server state:** product rows and embeddings are stored in PostgreSQL; uploaded product images are stored in RustFS. The database stores the image key, not the image bytes.
- **Browser-local state:** `src/cart/CartProvider.tsx` keeps cart items in a React context and persists them in `localStorage` under the key `cart`. It stores product fields, quantities, and a price snapshot. The provider hydrates after mount and writes changes back after hydration. `src/components/ChatWidget.tsx` keeps chat history in client memory; it is not written to `localStorage`.
- **Request-scoped chat input:** chat history, the current path, and the cart projection arrive at `/api/chat` with each request. The supplied route validates and uses them but does not write them to PostgreSQL or RustFS.

The cart reader only performs minimal shape filtering, and its source comment notes that the stored price is a snapshot and should be revalidated by a future server-side checkout. That checkout is not implemented in the current cart flow. The chat route does re-read prices when it calculates `viewCart`, but the client cart itself is not server-persistent.
